# pj-untrusted-input — 信頼できない入力の分類・検証(claude-deck3)

## 収録基準

**typecheck も vitest も通過し、敵対的入力を実際に投げてはじめて出た型**だけを載せる。
git 引数面の防壁は [[pj-git-route]] §2 にあるので、ここには書かない(相互リンクのみ)。

## 1. 正規化を全部先に済ませてから、全判定を走らせる

- **症状**: `javascript:` は弾けるのに `java%09script:` `%6Aavascript:` が素通しする
  (`%6A` はデコードすると `javascript:` そのもの)
- **機構**: `classifyHref` はスキーム判定を**生の文字列**に対して行い、パーセントデコードは後段の
  `resolveRelative` の中で走っていた。**判定と正規化が別関数に分かれている**ため、エンコード形が
  判定を素通りしてデコード後に復活する
- **打ち手**: 入力を受けたら **(1) デコード(収束するまで多重) → (2) 制御文字・空白の除去 →
  (3) パス区切りの正規化** を全部先に済ませ、**その 1 個の変数に対して全判定を走らせる**。
  生の文字列に対する判定も残して二層にする(どちらが落ちても安全側に到達させる)
- **1 件ずつ直さない**: この型は同一関数で **3 回連続で再発した**(パーセントデコード → `\` を
  区切りとして扱っていない → バックスラッシュ正規化がプロトコル相対 `//` 判定より後)。
  1 件見つけたら「その入力を弾く」ではなく**順序の構造ごと作り直させる**。個別修正の繰り返しは
  修正サイクルを浪費する(実測: 3 サイクル)
- **確認セット**(新しい分類関数を書いたら必ず通す): 生 / パーセント / 多重パーセント(`%2509`) /
  大文字小文字 / 制御文字混入 / `\` 区切り / エンコード UNC(`%5C%5Chost%5C...`) / 空文字 /
  `.` `./` `../` / プロトコル相対 `//`。**正常系(日本語ファイル名・空白入り・相対パス)が
  壊れていないこと**も同じセットで固定する

## 2. 二重防御が競合したら、片方を消さず下位の欠陥を直す

- **症状**: ライブラリ側の検査と自前の判定が食い違い、subagent が**ライブラリ側の検査を無効化**して
  自前判定に一本化してくる(実例: markdown-it の `validateLink` を `() => true` で潰した)
- **機構**: 二重防御は**役割が違うから 2 枚ある**。片方を消すと、残った層が将来退行したとき何も
  残らない
- **打ち手**: 競合の解消は「片方を消す」ではなく「**両方が同じ安全側の結論に到達するよう下位の
  欠陥を直す**」。上の実例では真因は `classifyHref('')` が空 href をディレクトリーへの相対リンクに
  誤分類していたことで、markdown-it は無関係だった。**brief で二重防御を要求するときは、
  この解消方針まで書いておく**

## 3. ライブラリの防御挙動は推測せず、実際の出力を並べる

markdown-it の `validateLink` が false を返すと、href が空になるのではなく**パース位置が進まず
リンク構文全体がテキストに落ちる**(`[x](javascript:alert(1))` は `<a>` すら生成されない)。
「危険な href が空文字で残る」という自然な想定は誤りで、実際に危険なのは元から空/ディレクトリー
のみの `[x]()` `[x](.)` だった。**防御の挙動を仮定して設計すると、守っている対象がずれる。**

## 4. 依存をセキュリティ境界に置くときの衛生

- **advisory 一覧は「使ってはいけない機能」のリスト**として読む。DOMPurify の既知 advisory はほぼ
  全部が `IN_PLACE` / `ADD_TAGS`・`ADD_ATTR` の関数形式 / `USE_PROFILES` / `addHook` / `setConfig` /
  `SAFE_FOR_TEMPLATES` に集中している。**バージョンを上げて満足せず、これらを使わない制約を
  brief に書く**。素直な `sanitize(html, {...})` だけで足りるはず
- **`npm audit` の件数だけ見て「依存を足したら脆弱性が増えた」と報告しない**。`npm audit --json` の
  **`nodes` フィールドで実際のパスを見る**。実例: dompurify の advisory は range `<=3.4.11` で
  該当ノードは `node_modules/monaco-editor/node_modules/dompurify`(monaco の入れ子・既存)のみ、
  トップレベルに入れた 3.4.12 は無罪だった

## 5. 制御文字を扱う実装は、文字コード比較で書かせる

**不可視の C0 制御バイトがソースに混入する事象を、別々の builder が独立に 2 回踏んだ**
(制御文字レンジの正規表現リテラルを書こうとして / 空文字列のつもりの箇所に)。
**typecheck も vitest も通過し、バイト走査でしか見つからない。**

- 実装は正規表現リテラルに生バイトを書かせず `codePointAt(0) <= 0x20` のような**文字コード比較の
  ループ**で書かせる
- 完了報告を受けた時点で **Conductor がバイト走査を回す**
  (`c < 9 || (c > 13 && c < 32) || c === 127` を数える)。`.claude/settings.json` の PostToolUse
  フックでも機械的に検出しているが、フックは新規/変更ファイルしか見ないので最終確認は自分でやる

## 6. セキュリティ境界の修正は、Conductor が自分の入力セットで叩き直す

builder のテストは **builder が想定した攻撃面しか覆わない**。実測: 「全パターン通過」と報告された
修正に、Conductor が自作プローブを当てたら 1 件穴が残っていた(エンコード UNC)。
さらに verifier/reviewer が報告した欠陥は、**必ず「同じ原因の別の入り口」を自分で横展開する**
(1 パターンの報告が横展開で 5 パターンに広がった実績)。

`npx tsx` で対象の純関数を直接叩く 30 行のプローブで足りる。**敵対的フィクスチャは実装前に作る** —
[[pj-isolated-verify]] の「フィクスチャの作り方」を参照。
