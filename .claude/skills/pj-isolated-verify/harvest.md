  LocalAppData を見失って解決できなかった (罠 2 はサーバー起動の話だけだった)。

  DOM から読めず**サーバーの snapshot を別ソケットで取って確認する**ことを明記した。
  代替案「offline エミュレーションだけで切断系を賄う」は退けた — 上記 16 のとおり
  作れる切断の種類が限られ、しかも空振りが「正常」と区別できない形で出るため。

## 009: リサイズ追従は子プロセスに言わせて測る + xterm は非表示なら DOM から読める (罠 23, 代替パターン改訂)

- date: 2026-08-30
- context: ターミナルパネルのグループ分割を検証していて、2 つの前提が崩れた。(1) 「セパレーターを
  動かしたらペインの幅が変わった」で合格にしかけたが、それはクライアントのレイアウトが変わった

  非発火も無症状に終わる)。(2) 罠の既存記述「xterm の画面内容は DOM から読めない」を額面どおりに
  受け取って snapshot 用の別ソケットを張りかけたが、実測すると**非表示のターミナルだけは
  `.xterm-rows` にテキストが載っていた**。WebGL addon が `visible=false` で dispose され
  DOM レンダラーに戻るためで、条件付きで DOM から読める。
- change: 罠 23 を追加し、代替パターンの「xterm の画面内容」を条件付き記述へ改訂。
  Why(罠 23) = 中間層 (ピクセル幅) の観測は、その先の伝播を保証しない。子プロセス自身に
  値を言わせれば末端まで通ったことが 1 発で分かり、**分割前後の 2 値が同じバッファに並ぶので
  再マウントしていないことまで同時に証明できる**。How = `"COLS=$($Host.UI.RawUI.WindowSize.Width)"`

  Why(改訂) = 「読めない」と書いてあると、安い経路があるのに高い経路 (別ソケット) を選ばせる。
  読めない条件は「表示中」に限る。

  スナップショット解析が要り、非表示ルートより明らかに高い。複数同時読み出しと
  「切り替えが観測対象を変える」場合に限って使う、と条件を明記する形にした。
  **代替案「スクリーンショットの目視でリサイズを判定する」も退けた** — 折り返し済みの既存行は
  幅変更後も再フローされないため、見た目からは追従の有無を判別できない。
- supersedes: —
- result: 同一ターミナルで分割前 `COLS=183` (1302px)、分割後 `COLS=90` (645px) を実測し、
