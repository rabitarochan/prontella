# pj-client-ui-state — クライアント状態・再レンダー・設定適用の定石(prontella)

## 収録基準

**コードレビューでもユニットテストでも原理的に捕まらず、実機で測って初めて分かった型**だけを載せる。
一般的な React の作法や、型検査で防げるものは載せない(そこに書いても読まれないため)。
1 項目は「症状 → 機構 → 打ち手」で 10 行以内。

## 0. 前提 — このプロジェクトではコンポーネントを回帰テストで守れない

`vitest.config.ts` の include が **`client/src/**/*.test.ts` のみで `.tsx` が対象外**、かつ
`@testing-library/react` も入っていない。したがって **`FilesTab` / `MarkdownPreview` 等の挙動は
ユニットテストで固定できず、実機検証だけが根拠**になる(実測: reviewer が挙げた指摘 3 件は全て
コード読解ベースで、回帰テストを書く手段が無かった)。

- コンポーネント寄りの変更を委任するときは、**実機の検証項目を厚くする**(green は無罪証明にならない)
- 「テストが通ったので安全」と報告されたら、それがコンポーネントの話なら**成立していない**
- 純関数に切り出せる判定(パス解決・分類・整形)は**最初から `.ts` に出す**。そこだけは守れる

## 1. 行レンダラーをコンポーネント関数の内側で定義しない

- **症状**: ファイルツリーの新規作成用インライン入力が 1〜2 秒ごとに消える。フォーカスは残るのに
  値だけが消える
- **機構**: react-arborist は `props.children` を「要素タイプ」として描画する。行コンポーネント
  (`Node`)を親コンポーネント関数の**内側**で定義すると、親が再レンダーされるたびに関数の
  identity が変わり、React は別の型とみなして subtree を unmount → remount する。ポーリング
  (App 4s / useTerminalSessions 3s)は再レンダーを起こす**引き金にすぎず、真因ではない**
- **打ち手**: 行レンダラー・セルレンダラーの類はモジュールトップレベルで定義する。親のスコープの
  値が必要なら props か context で渡す

## 2. ポーリング起因が疑われる UI 不具合は「値」より先に「ノードの同一性」を測る

- **症状の罠**: uncontrolled な入力(`value` なし + `autoFocus`)は remount されても
  **フォーカスは残り値だけ消える**。そのため原因が入力処理側(onChange・state 更新)にあるように
  見えて、調査が丸ごと誤誘導される
- **打ち手**: 「値が消えたか」ではなく **DOM ノードが差し替わったか(要素参照の同一性)** を先に測る。
  隔離環境で ①値のクリア時刻列 ②要素参照の同一性反転 ③API リクエスト送出時刻 の 3 系列を
  同時採取すると、因果が 3 方向から裏付けられて仮説の反証余地が消える
- **修正後の検証**: 「症状が消えた」だけを合格にしない。**ポーリングが従来周期のまま継続している
  こと**を検証項目に入れる(引き金を止めただけの見かけの修正を排除する。手法の一般形は
  `adversarial-verification` の §11)

## 3. 明示操作 > 設定ファイル

- **症状**: ステータスバーで改行コードを CRLF に変えて保存しても LF に戻る
- **機構**: 保存時整形(`FilesTab.tsx` の `formatOnSave`)が `.editorconfig` の `end_of_line` で
  モデルの EOL を**無条件に**上書きしていた。ユーザーの `pushEOL` が保存直前に打ち消される。
  なお **`.editorconfig` はマッチする全セクションをマージする**ため、対象拡張子のセクションが
  無くても `[*]` の指定は継承される(「拡張子の記載が無いから無関係」は誤った直感)
- **打ち手**: 設定ファイル由来の値とユーザーの明示操作が衝突しうる箇所では、**上書きフラグを
  持たせて明示操作を勝たせる**(`eolOverrideRef` が実装例)。EOL / インデント / 文字コードは
  すべて同じ形をしているので、どれか 1 つを触るときは他の 2 つも同じ形になっているか確認する
- **フラグの寿命**: `indentAppliedRef` と同じ寿命管理(closeTab / root 切替 / 再読み込みで解除)に
  揃える。**保存成功では解除しない**(同じタブで繰り返し保存しても選択が維持される必要がある)。
  タブを閉じると解除される = 選択は永続化されない。これは 2026-07-27 のユーザー判断による
  **意図した仕様であり、直すべき不具合ではない**。恒久的に強制したい場合は `.editorconfig` の
  `end_of_line` をメンテしてもらう、と案内する

## 4. 設定スナップショットの鮮度と自己参照

- **機構**: `.editorconfig` の内容はファイルオープン時のレスポンス(`FileContent.editorconfig`)に
  埋め込まれた**スナップショット**。設定ファイルを編集しても、開いているタブには反映されない
- **打ち手**: 設定内容をレスポンスに埋めてキャッシュするなら、**その設定ファイル自身の保存を
  無効化トリガーにする**(`GET /api/fs/editorconfig` で全タブ分を再取得する実装例がある)。
  再取得では `editorconfig` だけを差し替え、**`draft` / `content` / `encoding` / `hasBom` には
  触れない**(未保存の編集を破壊するため。`api.file` の使い回しが危険なのはこれが理由)
- **自己参照は 1 世代遅れる**: 設定ファイル自身の保存は、まだ更新前のスナップショットで整形される。
  `end_of_line = crlf` に書き換えたその保存自体は LF で書かれる。この経路は「更新は次回から」に
  なることを前提に設計し、ユーザーにもそう説明する

## 5. Monaco の機能は「エディターを 1 度も生成していない画面」で壊れる

- **症状**: Markdown プレビュー専用のセッション(エディタータブを一度も開いていない)で、
  `monaco.editor.colorize()` の出力がモノクロになる
- **機構**: `.mtkN` の配色 CSS は `standaloneThemeService` が**エディターインスタンス生成時に
  `<style class="monaco-colors">` を注入する**もので、colorize 単体では注入されない。さらに
  `json` のように **`onLanguage` で遅延登録される言語**は、colorize がモデルを作らないため
  登録が永久に走らず `_fakeColorize`(1 行 1 span)に落ち続ける
- **打ち手**: 使い捨ての 0 サイズエディター / 空モデルを 1 度だけ作って dispose し、
  テーマ注入と `onLanguage` を人為的に起こす。**登録完了は待たないと間に合わない**ので、
  fake かどうかを判定して解けるまでポーリングする(盲目的な 1 回リトライは遅いマシンで再発する)
- **検証項目に必ず入れる**: 「**エディタータブを一度も開かずに**その画面を開く」。
  ウォームな状態でしか試さないとすり抜ける(実測: これで json の着色漏れを 1 度見逃しかけた)

## 6. サードパーティ表示コンポーネントの内部 UI 状態は data の作り直しでは消えない

- **症状**: ファイルツリーを再読み込みすると、シェブロンもアイコンも「開いた見た目」のまま
  中身が 0 件になる。ユーザーは閉じる→開くの二度手間を強いられる
- **機構**: react-arborist の開閉状態は `data` prop から独立した内部ストア
  (`state.nodes.open.unfiltered`、ノード id がキー)に保持されており、**`data` を丸ごと
  差し替えても消えない**。そこへ再読み込みで `children` を `null` に戻すと、
  「開いている」という UI 状態と「子が未取得」というデータ状態が食い違う
- **打ち手**: 再取得系を実装するときは「データと UI 内部状態の**両方**を整合させる」ことを
  設計項目に立てる。開いているノードは children を保持したまま更新するか、
  内部ストア側の開閉も明示的にリセットする
- **一般化**: 開閉・選択・スクロール位置など、**サードパーティが自前で持つ UI 状態は
  props の入れ替えでは初期化されない**。自前実装(例: `BranchTree` の `expanded` は
  自分の `useState`)とは寿命の考え方が違うので、混在させるときに特に踏みやすい

## 7. Monaco を含むコンポーネントの再マウントは「入力直後」に限り Canceled 例外を漏らす

- **症状**: エディターグループの分割/畳み込み(`<Editor>` の再マウント)で、コンソールに
  `Uncaught (in promise) Canceled: Canceled` が出る。機能被害(スクロール飛び・IME 断)は無い
- **機構**: Monaco は dispose 時に in-flight の非同期処理(トークナイズ・ワードハイライト等)を
  CancellationError で中断し、それが未処理 Promise 拒否として浮上する。**アイドル状態の再マウント
  では出ず、「入力→即座に構造変更」でだけ出る**(切り分けプローブで実測 — idle の
  分割/畳み込み・最終タブ close・リロードはすべて例外ゼロ、type→split/collapse のみ再現)
- **打ち手**: VS Code 本体も cancellation はエラー扱いしない(onUnexpectedError で無視)。
  `monaco-setup.ts` で `unhandledrejection` を **name と message の両方が 'Canceled' のときだけ**
  preventDefault する(狭域フィルター。アプリ側の拒否を飲み込まない)
- **検証項目に必ず入れる**: 「**入力した直後に**再マウントを起こす構造変更」。アイドル状態の
  再マウントだけ試すとすり抜ける(§5 の「ウォームでしか試さない」と同型の罠)

## 8. コンテキストメニューから開くインライン入力は autoFocus が負ける

- **症状**: メニュー項目クリックで出したインライン入力(ツリーのリネーム等)が
  フォーカスされないまま表示される。見た目・値は正常なので目視では気づけない
- **機構**: Radix DropdownMenu は onSelect 後のクローズ処理(FocusScope)でフォーカスを
  動かす。input のマウント(autoFocus 発火)より後に走るため奪い返される。ContextMenu.tsx の
  `onCloseAutoFocus` preventDefault は「トリガーへ返さない」だけで、input への着地は保証しない
- **打ち手**: ref コールバックで `dataset` ガード付き `setTimeout(() => el.focus(), 0)` を
  1 回だけ仕込む(FileTree.tsx のリネーム/作成入力が実装例)。ツールバーボタン起動なら
  素の autoFocus で足りる — メニュー起動の経路を新設したときにだけ再発する
- **検証**: `document.activeElement === input` を実測する(スクリーンショットでは分からない)

## 9. サードパーティツリーの組み込みキーハンドラーはインライン入力と衝突する

- **症状**: ツリー内のインライン入力(新規作成・リネーム)に文字が入力できない。
  1 文字打つとフォーカスが一致する行へ飛び、blur ハンドラーが**中途の名前で確定**する
- **機構**: react-arborist のコンテナー `onKeyDown` にタイプアヘッド検索がある
  (default-container.js の `focusSearchTerm` — 前方一致行へ `tree.focus()` → 行 DOM へ
  フォーカス移動)。組み込みの `tree.isEditing` ガードは自前 input(disableEdit 運用)を
  保護しない。矢印キー・Backspace もツリー操作(行移動・onDelete)として解釈される
- **打ち手**: インライン入力の `onKeyDown` 先頭で**無条件に `e.stopPropagation()`**。
  キー種別で選別しない(タイプアヘッドは全印字キー、ナビゲーションは制御キーに反応する)
- **検証**: **打鍵イベント単位**で実際に文字を打つ(既存行名と前方一致する文字を選ぶ)。
  値の直接 set + Enter 合成では keydown 経路を通らず再現しない(実測: これで初回検証を
  すり抜け、ユーザー報告で発覚した)

## 10. 外部由来の再読み込みは <Editor> を差し替えず「重ねる」。モデルは URI から引く

- **症状**: 進行中表示のために `<Editor>` を別要素(プレースホルダー)へ差し替えると、
  カーソル/スクロール位置と undo 履歴が失われる。`keepCurrentModel` があるので安全に
  見えるのが罠 — 守られるのは**モデルだけ**で、再マウント時の `defaultValue` は既に
  存在するモデルには適用されない(表示は戻るが状態は戻らない)
- **打ち手**: `.editor-host` に `position: relative` を与え、**絶対配置のオーバーレイを
  重ねる**。既存の `common.loading` プレースホルダーは `<Editor>` と排他の分岐なので
  流用しない。さらに**短い処理では出さない**(150ms 遅延させる) — ローカル取得は
  10〜30ms で終わるため、毎回出すとウィンドウ復帰のたびに明滅して実害の方が大きい
- **反映先のモデルは `monaco.editor.getModel(Uri)` でパスから直接引く**。
  `editor.getModel()` の URI 一致を条件にすると、**応答が返るまでにそのタブから離れた
  ケース**で entry だけ新しくモデルが古いまま残り、戻ったときに表示と state が食い違う。
  viewState の保存/復元だけは「今そのモデルを表示している」ときに限る
- **検証項目**: ①スクロールした状態で外部変更 → 先頭行番号が保たれること
  ②「別タブへ切り替えた直後に応答が返る」経路 ③遅延注入で実際にオーバーレイが出ること

## 11. 「マウント時にだけ効く」プロップにライブラリー自身が更新する値を流し戻さない

- **症状**: タイル / エディターグループのリサイズハンドルが、稀にドラッグと逆方向に動く、
  または隣でないペインを動かす。再現手順が立たず、タイルを DnD で動かすと治ることがある
- **機構**: react-resizable-panels は Group のパネル配列を**登録時に `offsetLeft` /
  `offsetTop` で並べ替え**て保持する一方、ドラッグ時のセパレーター↔パネル対応は**その場の
  DOM 順**で作り直し、リサイズ計算は配列の**添字**で行う。`display:none` の下
  (TileWorkspace は非アクティブビューをこれで保持する) では offset が全て 0 になって
  並べ替えが引き分けになり、配列は登録順のまま残る。`Panel` の `defaultSize` は登録
  エフェクトの依存にあるため、ツリーの sizes を毎ドラッグ流し込んでいると**一部のパネル
  だけ再登録**が起きて順序が反転し、**Group が再マウントされるまで直らない**
  (DnD で治るのは構造キーで再マウントされるため)
- **打ち手**: 初期値プロップは**マウント時に凍結する** (`SplitPanel.tsx` の
  `useRef(initialSize).current` が実装例)。構造キーで Group が再マウントされる設計なら、
  分割・クローズ・DnD での最新値反映は保たれたまま、部分再登録だけが消える
- **一般化**: 渡すプロップが「初期値」か「制御値」かを必ず確認する。初期値プロップに自分の
  state を流し戻すと、**ライブラリー内部の再登録・再計測を毎回起こす**。それが計測不能な状況
  (`display:none`・0 サイズ) と重なったときだけ壊れるので、通常操作では踏まない
- **検証**: 再現手順が不明な不具合ほど**対照条件込みで測る**(表示中×部分再登録 /
  非表示中×全再登録 / 非表示中×部分再登録)。壊れた条件だけを見ると修正の効き目を測れない
  (真理値表の作り方は CLAUDE.md の「Verify the discriminator」)。
  **なお、アプリ内で「非表示中にサイズが変わる」発火経路は特定できていない** —
  機構と修正の有効性は実測済みだが、再発したら別機序を疑うこと

## 12. 接続の生死は close イベントで判定できない — 送信ガードが障害を無症状にする

- **症状**: 別アプリを触ってしばらくして戻ると、ターミナルが入力を受け付けず、パネルを
  リサイズしても TUI が追従しない。リロードすれば直る
- **機構**: (1) TCP が FIN 無しで死ぬ (スリープ・Wi-Fi 切替・VPN) と `readyState` は
  **OPEN のまま張り付き、`onclose` は永久に発火しない**。ブラウザーの WebSocket API は
  protocol ping/pong を JS に露出しないので、**アプリ層のハートビートを持たない限り
  この状態は観測できない**。(2) 送信側が `readyState === OPEN` でガードして黙って捨てる
  実装だと、**障害が画面にもコンソールにも出ない**。リサイズは `fit()` がローカルで走る
  ぶん「効いているのに追従しない」ように見え、切り分けが接続から逸れる
- **打ち手**: 接続は再接続 + ハートビート付きのラッパー越しに張る
  (`client/src/lib/liveSocket.ts`)。**ハンドルの identity を再接続をまたいで不変にする**と、
  呼び出し側は ref の入れ替え無しでクロージャーに捕まえておける。
  **再接続の `onOpen` で「接続直後に送るべき状態」(ターミナルなら resize) を必ず送り直す** —
  これを忘れると繋ぎ直っても症状が残る。サーバー側は id での再アタッチと snapshot 再生を
  既に持っているので、直すべきはクライアントだけ (`server/pty.ts` の `attach`)
- **一般化**: 「送れなければ捨てる」ガードを書くときは、**捨てたことが観測できる経路**
  (バッジ・カウンター) を同時に用意する。無音のドロップは後から「たまに効かない」という
  再現困難なバグとして返ってくる
- **検証**: 対照条件を必ず入れる — ①切断 → 復帰 ②半死 (ping 握り潰し)
  ③**何もせず放置して再接続が 0 件**。③が無いと「直った」のか「常時張り替え続けている」
  のかを区別できない (手法は `pj-isolated-verify` の代替パターンと罠 16-18)

## 13. ポーリングで配る一覧に「頻繁に変わる中身」を載せない — 顔ぶれと中身を分ける

- **症状**: サーバーの API は常に正しいのに、UI だけが 1 手ぶん古い。エージェントの
  実行中ツールが「終わったツール」を出しっぱなしになり、サブエージェントが消えても
  行が残る。リロードすると正しくなる
- **機構**: 一覧を配るフックがポーリング (`useTerminalSessions` は 3 秒) で、
  **プッシュ経路 (`/ws/events` → `useAgentEvents`) を見ていなかった**。ステータスのように
  数秒に 1 回しか変わらない値なら気づかないが、実行中ツールは**ポーリング間隔より短命**
  なので、ズレが常態になる。さらに厄介なのは、この症状が**状態機械のバグに見える**こと —
  「SubagentStop を送ったのに行が消えない」から実装を疑い、サーバー側を読みに行ってしまう
- **打ち手**: **顔ぶれ (作成・終了) はポーリング、中身はプッシュを被せる**。
  ポーリング結果を id でプッシュのストアに引き当てて差し替えるだけでよく
  (`sessions.map((s) => live[s.id] ?? s)`)、購読の配線も一覧の意味論も変えずに済む。
  プッシュに無い id はポーリングの値のまま残るので、初回ロードも壊れない
- **切り分け**: **サーバーの API とクライアントの DOM を同一スクリプトで同時に測る**。
  1 イベント送る → 両方を読む、を繰り返す。片方だけ見ていると「どちらの層が遅れているか」
  を区別できず、実際にこれで状態機械を無実のまま疑った。API が即座に正しく DOM だけが
  N 手遅れるなら、原因は配信経路であって状態ではない
- **一般化**: 一覧オブジェクトに新しいフィールドを足すときは、**そのフィールドの変化頻度が
  ポーリング間隔より速いか**を先に問う。速いなら、そのフィールドはポーリングで配ってはいけない
- **関連**: この症状を実際に出した hook 由来のフィールド設計は [[pj-agent-status-detect]] §8

## 14. 再マウントに耐えられない中身は host-div へ逃がす — Monaco と xterm は非対称

- **症状**: パネル内に分割を足した瞬間、ターミナルの WebSocket が張り直されスクロールバックが
  消える。**同じ設計を Monaco でやっても何も起きない**ので、実装中は気づけない
- **機構**: Monaco は モデル (`keepCurrentModel`) + viewState 復元で再マウントを生き延びるように
  作ってあるので、`GroupSplitView` はジオメトリ層だけで portal を持たない (§10 も参照)。
  xterm にはその復元経路が無く、`term.dispose()` で DOM ごと消えて接続も切れる。
  **同じ「分割ツリー」でも、リーフの中身によって必要な層数が違う**
- **打ち手**: 再マウントに耐えられない中身は **`TileGrid` と同じ host-div + `createPortal`**
  にする — id ごとに detached な div を 1 つ持ち、中身はそこへポータルし、ジオメトリ側の
  ペインは `appendChild` で**取り込むだけ**にする。分割もグループ間移動も DOM の移動に落ちるので
  インスタンスは生き残る (`TermPanel` / `TermGroupPane` が実装例)
- **`appendChild` は必ず冪等ガードで包む** (`host.parentElement !== body` のときだけ動かす)。
  同じ親の下でも appendChild は一度切り離して挿し直すため、**フォーカスと選択が黙って落ちる**
  (`TilePane.adoptHost` に同じガードがある理由)。3 秒ポーリング由来の再レンダーで毎回踏む
- **ポータルの描画順は木の走査順ではなく id で安定ソートする**。DnD の並べ替えで配列の並びが
  変わると、React の再調停で中身が remount されうる (`TileGrid` に同じコメントがある)
- **検証**: 「見た目が保たれた」を合格にしない。**DOM ノード参照の同一性 + `isConnected`** を
  操作前後で測り (§2 と同じ discriminator)、さらに**子プロセス側が本当に追従したか**まで測る
  (手順は `pj-isolated-verify` 罠 23)

## 15. 参照カウントの購読は「ポータル先の差し替え」で一瞬 0 に落ちる

- **症状**: 共有ポーリングを参照カウントで 1 本に束ねたのに、タイルを分割するたびに
  リクエストが 1 発余分に飛ぶ。購読者数のガード (`if (next > 1) return`) は正しいのに効かない
- **機構**: ヘッダースロットへ `createPortal` している UI は、タイルのジオメトリ変更で
  `TilePane` が remount → スロット DOM が差し替わる → **ポータルの container が変わるので
  React は unmount → mount する**。購読者が 1 → 0 → 1 と往復し、0 の瞬間にタイマーが止まり、
  再購読の「1 人目だから取りに行く」が即時 fetch を撃つ
- **打ち手**: 購読開始の条件を**購読者数ではなくタイマーの有無**にし、**十分新しい
  スナップショットがあれば即時 fetch を省く** (`usageStore.subscribe` が実装例)。
  「1 人目かどうか」は remount の往復で簡単に破れる前提に立つ
- **検証**: `fetch` をラップして呼び出し回数を数え、**タイルを分割した前後で増えないこと**を
  測る。「同時に 2 本走っていないこと」だけでは往復ごとの 1 発を見逃す

## 16. 永続化キーの移行・書き換えはバンドルより前に走らせる

- **症状**: 起動時に localStorage のキーを書き換える処理(改名に伴う移行、既定値の注入)を
  `main.tsx` の本体に置くと、**何も移行されない**
- **原理**: 各ストア(`theme/themeStore.ts`・`editorState.ts`・`i18n/langStore.ts`・
  `layout/*Store.ts` 等)は**モジュール初期化時**に `localStorage` を読む。ESM は import を
  先に評価するので、`main.tsx` の本体が動く頃には**全ストアが旧キー(= 存在しないキー)を
  読み終えて既定値で確定している**
- **打ち手**: `client/index.html` のインライン script で行う。FOUC 対策のテーマ読み出しより
  **前**に置く(でないと初回ペイントだけ既定テーマになる)。走査は `localStorage.length - 1`
  から**末尾方向へ**(途中でキーを消すため)。新キーが既にあれば旧キーは捨てる
- **やらない**: 「移行モジュールを `main.tsx` の先頭で import する」は、import 並べ替えの
  整形ツールやリンターで簡単に壊れる。**評価順序を人間の規律に頼らせない**
- **検証**: 実ブラウザーで「旧キーを仕込む → ロード → ダンプ」。仕込みは
  `Page.addScriptToEvaluateOnNewDocument`(ページスクリプトより前に走る)。
  **移行が先に走った証拠は「移行後の値でテーマが初回ペイントから適用されていること」で取る** —
  キーの中身だけ見ても順序は分からない

## 17. react-resizable-panels で分割を足すときの Panel/Group 契約

- **症状**: ペインが指定した幅にならない(`20%` のつもりが 16.7%)。あるいは
  `overflow-y: auto` を持つペインがスクロールしなくなる。どちらも typecheck も vitest も
  **コードレビューも通過**し、実機で幅とスクロール量を測って初めて出る
- **機構**: (1) `defaultSize` は **全パネルで正規化される**。片方を `20%`、他方を `100%` の
  ままにすると 20/(20+100) = **16.7%** に縮む(実測 2026-09-02: 260px のつもりのツリー列が
  216px)。`SplitTreeView` が分割ツリーの sizes を常に合計 100 に正規化しているのはこのため。
  (2) `Panel` は div を **2 枚**描画し、`className` と `style` は**内側**に付く。内側の既定は
  `overflow: auto` で、それを `SplitPanel` が `overflow: hidden` で固定するため、ペイン側
  クラスの `overflow-y: auto` はインラインに負ける
- **打ち手**: 2 ペイン分割のサイズは**両方まとめて算出**して合計 100% にする
  (`layout/paneWidths.ts` の `paneSplitSizes()` が実装例)。ペイン自身をスクロールさせるなら
  `SplitPanel` の `style` で上書きする。**下限・上限は `minSize`(`"120px"`)が両側に効くので
  自前の clamp は書かない** — 狭いタイルでも隣が潰れない
- **Group の子はパネルとセパレーターだけ**にする。コンテキストメニュー・モーダル・ダイアログは
  Group の外(従来のルート div)に残す。`Group` は残りの props を root div へ spread するので
  既存の `onPointerDownCapture` 等はそのまま渡せる(`ref` だけは `elementRef` にする)
- **パネル id は DOM の `id` 属性になる**。同じパネルが複数タイルに出る画面では `leafId` を
  前置しないと id が重複する
- **誤診しやすい点**: (1) は「px の `defaultSize` がレイアウト確定前に測られている」と読める
  — 数字が一度それらしく合ってしまう。**px と % を兄弟で混ぜず % で合計 100 に揃えれば、
  測定タイミングの議論自体が消える**
- **検証**: 「幅が変わった」を合格にしない。**ドラッグ量と実測 px の差・隣接ペインの符号**を
  測り、対照条件(表示中 / 一度隠して戻す / タイル分割後)を揃える(§11 の破壊は逆方向・
  非隣接として出る)。既定値の確認は **localStorage を消してリロードしてから**行う

## 18. iframe は「移動で死ぬ」第 3 の階層 — React ツリー外の固定オーバーレイへ逃がす

- **症状**: タイルを分割・移動しただけで埋め込んだ VS Code が再ロードされ、
  実行中のデバッグセッションが飛ぶ
- **機構**: §14 は「Monaco は再マウントに耐える / xterm は耐えない」という 2 段階だったが、
  iframe は**さらに上の階層**にある。host-div + `createPortal` は再マウントを DOM の**移動**へ
  落とすことでインスタンスを守る設計だが、**iframe は移動そのもので中身が再ロードされる**
  (`appendChild` は同じ親の下でも一度切り離して挿し直すため。§14 の冪等ガードと同じ機構が、
  こちらでは致命傷になる)。加えて `App.tsx` はワークツリー切替でタイル木ごと remount するので、
  木の中に置く限り逃げ場が無い
- **打ち手**: **React ツリーの外**にモジュールレベルのシングルトンとして iframe を持ち、
  `<main>` 直下に一度だけ挿して**以後 DOM 上を一切動かさない**。タイル側には空の
  プレースホルダー div だけを描き、その `getBoundingClientRect()` に `position: fixed` の
  オーバーレイを追従させる。`VncView` (worktree の key remount の外に置く) が先行例
- **可視状態を矩形から推測しない**。§14 のポータル層は `visited` パターンでビュー切替時に
  パネルをアンマウントしないので、「隠す」きっかけが自然には来ない。`setOverlayVisible(el, next)`
  で**明示的に渡す**こと。矩形が 0 かで推測した実装は実測で破れ、git へ切り替えても
  iframe が上を覆ったままになった (`elementFromPoint` がオーバーレイを返す)
- **rAF は連続発火のまとめにしか使わない**。`requestAnimationFrame` はタブが背面に回ると
  走らないので、`rafId` を立てて待つ実装は**そこで永久に no-op 化**し、以後すべての同期が死ぬ。
  attach / 表示切替 / レイアウト変更のような**離散的なきっかけは同期で反映**し、
  rAF は resize / scroll / `ResizeObserver` にだけ使う
- **ポインターを吸わせない**: iframe はポインターイベントを吸うので、タイル DnD 中は
  コンテナごと `pointer-events: none` にする。z-index はドロップ表示・通知・モーダルより**下**
  (10) に置き、それらが iframe の上に出るようにする
- **検証**: 「画面が残って見える」を合格にしない — **再ロード後でも成立する**。
  `contentWindow` に載せたカウンター、または Network で workbench の初期リクエストが
  再発行されていないことで**再ロード回数 0** を測り、各操作後に矩形のズレも px で測る
  (実測 2026-09-06: 分割 / クローズ / ビュー切替往復 / resize すべてで再ロード 0・ズレ 0px)
- **実装の所在**: `client/src/components/vscode/overlayHost.ts`
  (`attachOverlay` / `detachOverlay` / `setOverlayVisible` / `syncOverlay` / `setOverlayInert`)。
  ⚠ **`feat/vscode-tile` ブランチにのみ存在し `main` には未マージ**
  (埋め込み自体は体験上の理由で不採用。経緯は skdd-harvest の backlog を参照)。
  この節の知見は「DOM 移動で死ぬ中身」一般に効くので、埋め込みの採否とは独立に残す

## 19. N>1 前提の協調プロトコルを、N=1 で無条件に適用しない

- **症状**: 単一タブ・単一表示なのに、ターミナルだけが枠より小さく描画される。
  クリックすると直る。再現には**エージェント実行のような負荷**が要り、放置では出ない
- **機構**: PTY の winsize は「表示中のページが主張し、他は追従する」形で調停している
  (複数ページが同じセッションを見ると、最後に送った値で全員のレイアウトが壊れるため)。
  この「非アクティブなら譲る」規則を**無条件**に書いたので、何かの拍子に `pageActive` が
  false のまま戻らないと、**譲る相手がいないのに永久に譲り**、自分のサイズを一度も
  主張しないまま縮んだ状態で固定された。§12 と同じく「送信ガードが障害を無症状にする」型だが、
  こちらは接続ではなく**調停条件**が原因なので、切り分けが接続へ逸れると外す
- **打ち手**: **譲る条件に「他に視聴者がいること」を入れる**。サーバーが `viewers`
  (= そのセッションに繋がっているソケット数) をスナップショットとブロードキャストで配り、
  クライアントは `pageActive || soleViewer` のときだけ主張する
  (`XTermView.tsx` の `canClaim()`、`server/pty.ts` の `broadcastViewers()`)
- **一般化**: 「他者に譲る」「先に取った者が勝つ」「アクティブな方が主張する」系の規則を
  書いたら、**参加者が 1 人のときに自滅しないか**を必ず確認する。N=1 は最も普通の
  使われ方なのに、N>1 を想定して書いた条件の**テストケースからは抜け落ちる**
- **検証**: 修正を**外した状態**との A/B で測る。実測 2026-09-06: 修正を外すと 2560px の
  コンテナで 800x498 に縮み、戻すと 2540x2100 になった。負荷依存で再現性が低いので、
  「直ったように見える」だけでは修正の寄与と偶然を区別できない。
  ユーザー環境での採取には `scripts/term-size-probe.js` (読むだけ) を使う

## 20. 遅延読み込みツリーの reveal は「祖先を先に埋める」— open state はデータより先に立つ

- **症状**: 開いているファイルにツリーの選択を追随させたいのに、閉じたフォルダー配下だと
  ハイライトもスクロールも起きない。`selectedPath` は正しく渡っている
- **機構**: ツリーが遅延読み込み(`children: null` = 未取得)だと、**一致すべき行が `data` に
  そもそも無い**。さらに仮想化(react-window)で可視域外の行は DOM にも無いため、
  「rows に見えない」を「展開されていない」と読み違えやすい
- **打ち手**: (1) 祖先を**浅い順**に列挙し、未取得の階層だけ並列に取得して**1 回の setState で
  浅い順に畳み込む**(親が木にいないと子をマージできない)。(2) `TreeApi.open(id)` は
  **`data` に無い id でも通る**(redux へ dispatch するだけ)ので、取得前に立ててよい —
  次のツリー再読み込みで「開いている dir」として拾われる副作用も味方になる。
  (3) スクロールは `idToIndex`(= 展開済み全ノード。描画済み行ではない)に id が入ってから
- **罠**: `TreeApi.scrollTo` の内部 `waitFor` は**リトライ上限で reject したあとも
  `setTimeout(check, 10)` を止めない**(react-arborist 3.16 `utils.js`)。現れない id を
  渡すと 10ms 周期のタイマーが**永久に残る**。自前で有限回だけ待って
  `id in tree.idToIndex` を確かめてから呼ぶ(その時点なら初回チェックで即 resolve する)
- **一般化**: 再発火の条件に**「描画できる状態か」(ホストの高さ > 0)を入れる**。パネルが
  `display:none` のあいだは行が 0 個で諦めるしかないので、**可視化された瞬間に仕切り直す**
  経路が無いと「検索パネルから開いたファイルだけ追随しない」という穴になる
- **検証**: 残留ポーリングの不在は `window.setTimeout` をラップして**delay === 10 の呼び出し数**を
  数える(削除済みファイル / 祖先ごと消えたパスへ切り替えて 0 のままを確認。2026-09-10 実測)。
  祖先の展開は仮想化のせいで `rows` が当てにならないので、**スクロールを 0 へ戻してから**見る
