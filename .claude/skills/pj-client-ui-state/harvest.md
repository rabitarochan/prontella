## 006: 接続の生死は close イベントで判定できない (§12)

- date: 2026-08-29
- context: 「ブラウザーで別のアプリを操作してしばらくして戻ると、ターミナルが入力を
  受け付けず、パネルをリサイズしても追従しない。リロードすれば直る」というユーザー報告。
  ユーザー自身も「xterm.js の挙動を理解していないので的外れかもしれないが、定期的に
  接続を確認して繋ぎ直してほしい」と、機構ではなく打ち手の形で要望を出していた。
  調べると `XTermView` の WebSocket には `onclose` も `onerror` も再接続も無く、
  入力とリサイズは両方 `readyState === OPEN` でガードされて**無言で捨てられて**いた。
  サーバー側は同じ id での再アタッチとスクロールバック / DEC モード再生を既に持っており、
  受け皿は完成していた。
- change: §12 を追加。Why = (1) TCP が FIN 無しで死ぬと `readyState` は OPEN のまま
  張り付き `onclose` が永久に来ない。ブラウザーは protocol ping/pong を JS に露出しないので、
  **アプリ層のハートビートを持たない限りこの状態は観測できない**。(2)「送れなければ捨てる」
  ガードは障害を画面にもコンソールにも出さないため、切り分けが接続から逸れる
  (リサイズは `fit()` がローカルで走るぶん「効いているのに追従しない」ように見える)。
  How = 再接続 + ハートビート付きラッパー (`client/src/lib/liveSocket.ts`) 越しに張り、
  ハンドルの identity を再接続をまたいで不変にする。**onOpen で「接続直後に送るべき状態」
  (ターミナルなら resize) を必ず送り直す**。代替案「`onclose` で 3 秒後に張り直すだけ」
  (`agentEvents.ts` の従来実装) は退けた — 半死ソケットでは `onclose` 自体が来ないため、
  ユーザーが踏んだ経路をまったく塞げない。検証には「何もせず放置して再接続 0 件」の
  対照条件を必須項目として明記した。
- supersedes: —
- result: 隔離実機で 7 シナリオ PASS。半死は 16.3 秒で検知して張り替え、切断中に縮めた
  幅は復帰後に PTY へ届いて 319 → 86 桁に追従、サーバー再起動後は「セッションは失われました」
  で打ち切り (再試行ループ無し)。対照の 150 秒放置では再接続 0 件・コンソールエラー 0 件。
  ユニットテスト 14 件 (`liveSocket.test.ts`) で再接続・ハートビート・打ち切りを固定した。

## 008: 再マウント耐性はリーフの中身ごとに違う + 参照カウント購読は remount で破れる (§14, §15)

  タイルヘッダーへポータルする実装で、参照カウントによる共有ポーリングがタイル分割のたびに

- change: §14 と §15 を追加。§14 の Why = 「分割ツリー」の実装が同じでも、リーフの中身が

  3 経路すべてに退避を挿す必要があり、1 つ漏らすと無症状で壊れる (appendChild による

  **実装中に自分が入れた欠陥 2 件を決定則として昇格させた**: (a) 可視状態を矩形から
  *推測*してはいけない — `visited` パターンではビュー切替でアンマウントされないので
  「隠す」きっかけが来ず、実測で git パネルを iframe が覆ったままになった。
  `setOverlayVisible` で明示的に渡す。(b) rAF はタブが背面に回ると走らないので、

  §19 Why = winsize の調停 (表示中のページが主張し他は追従) を**無条件**に書いたため、

  負荷依存で特定しきれず、仮に 1 経路潰しても「譲る相手がいないのに譲る」という

## 012: 遅延読み込みツリーの reveal と、ライブラリー内蔵ポーリングの止まらなさ (§20)

- date: 2026-09-10
- context: ファイルパネルに VS Code の `explorer.autoReveal` 相当を実装した。ハイライト自体は
  既に `selectedPath` で同期していたが、遅延読み込みのため閉じたフォルダー配下では
  行が `data` に存在せず何も起きなかった。実装前に react-arborist の実装を読み、
  `TreeApi.scrollTo` が使う `waitFor` が**上限で reject したあともポーリングを止めない**
  ことを見つけた(`utils.js`: `tries === 100` で reject するが `setTimeout(check, 10)` は
  そのまま続く)。素直に `scrollTo` を呼ぶ設計だと、削除されたファイルへ切り替えるたびに
  止まらないタイマーが 1 本ずつ増える。
- change: §20 を追加。Why = 遅延読み込み + 仮想化のツリーでは「行が見えない」原因が
  データ・開閉状態・スクロール・描画可否の 4 つに分かれ、どれを疑うかを先に決めないと
  切り分けが発散する。How = 祖先を浅い順に 1 回の setState で畳み込む / `open(id)` は
  データ不在でも立つので先に立てる / `idToIndex` に入ってからスクロールする /
  再発火の条件にホスト高さ > 0 を入れる。**代替案「`scrollTo` に任せて `.catch()` だけ
  付ける」は退けた** — reject は 1 回しか起きず、その後もポーリングは走り続けるので
  catch では止まらない。「ライブラリーが Promise を返すなら後始末もしてくれる」という
  推測が成り立たない実例として残す。
